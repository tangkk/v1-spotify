# v1-spotify

English | [简体中文](README.zh-CN.md)

A self-hosted Spotify web player/controller (served at `https://spotify.example.com/spotify`). It is a single-file Python service (standard-library `ThreadingHTTPServer`, with the frontend page embedded in `SPOTIFY_PAGE`). The browser tab registers itself as a Spotify Connect device through the Web Playback SDK; the server ("V1") handles OAuth, proxies the Web API, and keeps its own play queue and favorites.

Split out of the author's private deployment repository with `git filter-repo`, keeping the full commit history of these files.

## Deploy on your own server

### ⚠️ Read this first: the service has no login

`spotify-server.py` **does no authentication at all**. Anyone who can reach it can control your Spotify playback and change your queue and favorites, and `/spotify-api/player-token` hands out your account's access token. Therefore:

- Keep it listening on `127.0.0.1` (the default; do not change it to `0.0.0.0`) and expose it **only** through a reverse proxy that requires authentication. The example below uses Caddy's `basic_auth`; the author uses `forward_auth` to a separate login service (see `Caddyfile.snippet`).
- It is single-user by design: one instance is bound to one Spotify account, and everyone who gets past the auth shares that account.

### Requirements

- A Linux server (the examples use systemd) with **Python 3.9+**. Standard library only, nothing to `pip install`.
- A domain pointing at the server, with HTTPS (Spotify requires an https redirect URI for anything other than `127.0.0.1`; Caddy obtains certificates automatically).
- A **Spotify Premium** account (playback-control endpoints return 403 for free accounts, and the Web Playback SDK does not work with them).

### 1. Create an app in the Spotify developer dashboard

1. Open <https://developer.spotify.com/dashboard> → Create app.
2. Set the **Redirect URI** to `https://your-domain/spotify-api/callback`. It must match `SPOTIFY_REDIRECT_URI` below exactly.
3. Under **APIs used**, tick *Web API* and *Web Playback SDK*.
4. A new app is in Development Mode, where only accounts listed under **User Management** can authorize it — add your own Spotify account's email there. See *Spotify platform limits* in the design notes below for Development Mode quotas.
5. Note the Client ID and Client Secret.

### 2. Install the service

```bash
# On the server (as root), from a clone of this repository
mkdir -p /opt/spotify
cp spotify-server.py /opt/spotify/server.py
cp spotify-server.env.example /opt/spotify/spotify.env
chmod 600 /opt/spotify/spotify.env
$EDITOR /opt/spotify/spotify.env                      # fill in SPOTIFY_CLIENT_ID / SPOTIFY_CLIENT_SECRET

cp spotify-server.service /etc/systemd/system/spotify-server.service
$EDITOR /etc/systemd/system/spotify-server.service    # set SPOTIFY_REDIRECT_URI to your domain
systemctl daemon-reload
systemctl enable --now spotify-server
curl -s http://127.0.0.1:8793/health                  # {"ok": true}
```

| Environment variable | Default | Notes |
|---|---|---|
| `SPOTIFY_CLIENT_ID` / `SPOTIFY_CLIENT_SECRET` | empty | Required. Keep them in `spotify.env`; never commit them to any repository |
| `SPOTIFY_REDIRECT_URI` | `http://127.0.0.1:8793/spotify-api/callback` | Must be changed for a public deployment; must match the developer dashboard |
| `SPOTIFY_HOST` / `SPOTIFY_PORT` | `127.0.0.1` / `8793` | Listen address |
| `SPOTIFY_DB` | `/opt/spotify/tokens.db` | SQLite: refresh token, queue, favorites, play history, catalog cache. Back this file up and you have backed up everything |

If `python3` is not at `/usr/bin/python3`, adjust `ExecStart` in the unit file.

### 3. Reverse proxy (Caddy example)

The page lives at `/spotify` and the API at `/spotify-api/*`; both routes must sit behind authentication:

```caddy
spotify.example.com {
	basic_auth {
		# generate the hash with: caddy hash-password --plaintext 'your-password'
		me $2a$14$REPLACE_WITH_HASH
	}
	handle /spotify-api/* {
		reverse_proxy 127.0.0.1:8793
	}
	handle /spotify* {
		rewrite * /spotify
		reverse_proxy 127.0.0.1:8793
	}
	redir / /spotify
}
```

Run `systemctl reload caddy`, open `https://your-domain/spotify`, enter the basic-auth password, and click **Connect Spotify** to authorize once. From then on, pressing play in the page turns that browser tab into a Spotify Connect device named "V1 Spotify Player".

Any other proxy (nginx, etc.) works the same way: forward `/spotify` and `/spotify-api/` to `127.0.0.1:8793`, put auth in front, keep HTTPS.

### 4. Updating

```bash
cp spotify-server.py /opt/spotify/server.py
python3 -m py_compile /opt/spotify/server.py && systemctl restart spotify-server
```

Database tables are created or extended at startup; upgrades need no manual migration.

### Trying it locally

```bash
SPOTIFY_CLIENT_ID=... SPOTIFY_CLIENT_SECRET=... SPOTIFY_DB=./tokens.db python3 spotify-server.py
```

Add `http://127.0.0.1:8793/spotify-api/callback` to the app's Redirect URIs in the developer dashboard, then open <http://127.0.0.1:8793/spotify> (it only listens on localhost, so no auth is needed for a local trial).

## Design notes

A standalone service, `spotify-server.service` (`127.0.0.1:8793`). Caddy forwards two authenticated routes to it, `/spotify` and `/spotify-api/*` (both behind the same `forward_auth /auth/check`), so no new DNS name is needed. The server only manages OAuth tokens and proxies Spotify Web API search/browse and playback control; audio and cover-art bytes never pass through it — the Spotify Web Playback SDK in the browser talks to Spotify directly, and the browser tab itself registers as a Spotify Connect device ("V1 Spotify Player").

- **Prerequisites**: a Spotify Premium account (playback-control endpoints return 403 for free accounts). On first use, click "Connect Spotify" at `https://spotify.example.com/spotify` to go through OAuth once. There is no separate "Enable Playback" step: the Web Playback SDK's `connect()`/`activateElement()` are deferred until they can be triggered synchronously inside your first click on a play button, satisfying iOS/Safari's rule that audio unlock must happen inside a real user gesture. `ensureDevice()` always prefers sending playback commands to *this browser's own* SDK device (waiting up to 15 seconds for it to connect if necessary; raised from 12 s on 2026-09-22) rather than to whatever device happens to be active, so sound comes out of the device you pressed play on. When that wait expires it no longer asks `/spotify-api/devices` just once and reports "no device available" — Spotify's device list can lag behind the connection actually being ready, so it now polls up to 4 more times (1.5 s apart, showing a "Connecting to Spotify…" toast) before really failing; this also gives a second chance when the `sdk.scdn.co` script hadn't finished loading and `connect()` was never triggered. Previously that message was a false alarm hit during those few seconds while the script was loading or the connection wasn't ready yet; changed 2026-09-22.
- Only the `refresh_token` is persisted (in `/opt/spotify/tokens.db`); the `access_token` is cached in memory only and silently renewed with the `refresh_token` shortly before it expires. The Spotify app's `client_id`/`client_secret` are injected from `/opt/spotify/spotify.env` (not in the repository); treat them like any other server secret and don't paste them anywhere else.
- **Enter in the search box = best match**: the three search icons (Artist/Album/Track) pick a type explicitly; the keyboard's Enter/Search key does not repeat the last-clicked type but calls `GET /spotify-api/search/best` — a single Spotify request with a comma-separated `type=artist,album,track` searches all three types at once (same cost as a single-type search, not 3×). Whichever type's top result exactly equals the query (ignoring case and surrounding whitespace) wins; next, if the top track (then the top album) has its title **and** one of its artists both appearing in the query (whole words, ignoring punctuation and order, with suffixes like " - Remastered"/"(Live)" stripped from the title), Track/Album wins — so typing "along came betty, pat martino" and pressing Enter goes straight to Pat Martino's Along Came Betty (added 2026-10-07); if nothing matches it falls back to Artist (the same as when Enter always meant Artist). Spotify offers no cross-type relevance score, so this is the closest available approximation of "most relevant".
- Search is organized around artists/albums: the artist page lists albums grouped into Album/Single/Compilation. "Build deduplicated track list" groups tracks by normalized title (album type first: studio album > single > compilation > appears_on; within a type, the earliest release wins — i.e. it prefers the original studio recording over later Remaster/Live/Deluxe reissues) and keeps the other versions expandable so you can pick a different one by hand. This is not exact matching, just simple deduplication. Scoring by the track `popularity` field was considered, but this Development Mode app no longer receives `popularity` at all (neither the single nor the batch endpoint returns it), so that dimension was dropped; ordering is purely by album type + release date.
- **Spotify platform limits (verified 2026-09-18)**: for this app, every paginated endpoint (search, artist albums, album tracks) has its `limit` parameter hard-capped at 10; anything above 10 (even documented legal values like 20 or 50) returns `{"error":{"status":400,"message":"Invalid limit"}}`. The batch endpoint `/v1/tracks?ids=...` returns 403 Forbidden outright; the single-track `/v1/tracks/{id}` works but no longer carries `popularity`. More seriously, `/v1/artists/{id}/albums` has its own **daily quota** (`QUOTA_EXCEEDED`, 429, `retry-after` measured at roughly 20 hours). It was exhausted once on 2026-09-18 from repeatedly browsing/testing artist pages; artist pages were completely unavailable during that time, while search and playback control were unaffected (quotas are per endpoint, not a ban on the whole app). None of these are bugs in this service; they are Spotify's restrictions on Development Mode apps without extended quota. The `SPOTIFY_PAGE_LIMIT=10` constant in `spotify-server.py` reflects these measurements, and "Build deduplicated track list" — very expensive per request, since every album of an artist needs its own tracks lookup — has been hidden from the artist page (the backend endpoint and code are still there; only the entry point is hidden). If the app is ever granted extended quota, `SPOTIFY_PAGE_LIMIT` can be raised and the dedup button brought back.
- **Permanent catalog cache**: to cope with the daily quota above, `tokens.db` has a `catalog_cache` table (`cache_key`/`payload`/`cached_at`, no expiry). `fetch_artist_albums`, `fetch_album_tracks` and `fetch_album_meta` all check this table first and only call Spotify on a miss. An artist's full album list, and each album's metadata and tracks, once requested, are read from SQLite forever and never cost quota again (measured: 0.3 s for a cold real request, 0.02 s from cache). There is currently no invalidation or cleanup: an artist's new releases won't appear automatically, and the corresponding `cache_key` has to be cleared by hand (there is no admin UI; edit SQLite directly).
- Playback controls (next/previous/volume/seek) all go through `/spotify-api/player/*`; **play/pause is handled locally by the SDK** (`togglePlayPause` → `state.player.pause()/resume()`). It used to be four serial steps — get device → GET now-playing → PUT pause → GET now-playing again — and with each server-to-Spotify call taking about 0.3 s, a click took over a second to register. Right after a page reload, before the SDK has state, it takes the slow Web API path. `?fastplay=0` switches back to the slow path for comparison (remembered; `?fastplay=1` turns it back on). The silent element's "unlock" (play+pause) only happens if it has never actually played, not on every click — otherwise it would collide with the moment the SDK resumes playback.
  - **One action at a time** (`playPauseBusy` lock): after you press play, the button is disabled immediately, and a second press (whether a repeat click, a pause, or one coming from the lock screen/headphone buttons) is simply ignored until this play has actually landed (the SDK's `resume()`/`pause()` promise resolves); only then is the button clickable again, and only then does pause really execute. Before 2026-09-23, a click optimistically flipped the icon immediately, re-verified separately 2 s later and re-sent the command via the Web API if needed, plus there was an extra "trust my own click for 3 s and ignore polling" window (`localPlayIntent`). Stacked together, these layers often caused glitches on rapid clicks: the icon flipping back, pause turning into a replay, and so on. All of it is gone now: one click maps to exactly one command and one state update; only if the SDK fails does it fall back to a single Web API attempt; no background timers, no "trust myself" window. Offline tests cover: a double click sends only one command; an opposite-direction second click is ignored; three synchronous clicks take effect once; the SDK and Web API paths are each verified. The player bar has real drag-to-seek (no longer a read-only progress bar), and the progress bar sits on the top row of the player bar so that dragging along the bottom edge of an iOS screen isn't stolen by the system swipe gesture. The header gained Recently Played (clock icon) and Play Queue (list icon) entries, both left of the favorites star; `GET /spotify-api/recently-played`, `GET /spotify-api/player/queue` and `POST /spotify-api/player/queue` (add to queue without interrupting playback) need the `user-read-recently-played` scope, added 2026-09-18 — accounts authorized before that need to disconnect and reconnect once.
- Playback continuity: clicking any track in an album plays the whole album starting from that track (via `context_uri` + `offset`) instead of stopping after one song; Spotify continues through the rest of the album within that context. Cross-album auto-advance no longer requires having navigated in from the artist page: `advanceAlbumQueue()` prefers the known `state.albumQueue` (only present when you entered from a group on the artist page) and otherwise lazily queries `GET /spotify-api/albums/<id>/next-in-artist` once. That lazy lookup also goes through the permanent cache above — a cold start makes at most one `artists/{id}/albums` call (a single page of 10, not full pagination), and after that the same artist + album type is free forever. Single-track clicks and "Play all" in the dedup list use a bare `uris` queue, which clears `state.albumQueue`; that and album auto-advance are two independent mechanisms.
- **Queue (maintained by V1, not read from Spotify's queue)**: the Spotify Web API can only add to the queue — there is no remove/clear endpoint, and it can't tell manual from automatic entries — so the queue is owned entirely by V1: `queue` in `tokens.db`'s `app_settings` (JSON: `manual` section, `auto` section, and `next`, the one already handed to Spotify) and `autoplay` (**off by default**). The manual section always precedes the auto section; the divider between them is the boundary line on the page, and each item carries a `manual`/`auto` label. `+` just appends to V1's manual section (`POST /spotify-api/queue/add`); if the track is already in the auto section it is moved to the end of the manual section (label changes from auto to manual). The autoplay switch (`PUT /spotify-api/queue-settings`): on → the auto section is "a mix of the last few manual items": the last 4 distinct albums in the manual section (topped up with `next`, or the current track if the manual section is empty) serve as seeds. Each seed contributes first the tracks after it in its own album, then the same artist's subsequent albums (same type, newest to oldest): at least 3 albums (`AUTO_ALBUMS_PER_SEED`), continuing further back while it has fewer than 12 tracks (`AUTO_SEED_TRACK_TARGET`), up to 10 albums (`AUTO_ALBUMS_PER_SEED_MAX`). For single-heavy artists (one "album" = 1 track), a fixed 3 albums yielded only 3 tracks; on 2026-09-22 this changed from "always 3 albums" to "3 albums minimum, keep going until there are enough or the safety cap is reached", so an artist with many singles no longer stops right away. When everything has been walked (`find_next_album_for_artist` returns None, i.e. this artist really has nothing earlier of this type) it stops early; a small count then genuinely means there's no more material, not a bug. Multiple seeds are interleaved 6 tracks per turn (`AUTO_CHUNK`; it only affects how many consecutive tracks each album gets while alternating between seeds — with a single seed everything available is taken anyway, so this number doesn't change the total; raised from 3 to 6 on 2026-09-22 so a single album appears in a more continuous run), newest seed first; tracks already in the manual section or `next` are removed, and the total is capped at 30 (`AUTO_CAP`). Finding the next album is lazily paginated (10 per page, each page cached permanently, up to 12 pages — so a cold cache costs at most 12 `artists/{id}/albums` calls per artist + type. It used to be 5 pages; for an artist like Joe Pass with over a hundred albums, a 1974 album sits on a late page, and without reaching it there was no "next album", leaving the auto section with only the rest of the current album). When the album isn't on any fetched page it falls back to release date, instead of only looking at the newest 10. Off → only the auto section is cleared; the manual section is untouched. While on: ① the auto section is consumed as it plays; when each new track starts, if fewer than 15 remain (`AUTO_LOW`) the driver tops it back up to at most 30 (once per track, in a background thread, without blocking the handoff); ② adding or removing manual items immediately recomputes from the new "last few manual items"; ③ when both manual and auto sections have run out, a new batch is computed from the current track in its last 15 seconds; ④ tracks you remove from the auto section with × are remembered in `auto_removed` (the most recent 200) and won't be put back by top-ups or recomputation. Each item's × is a pure V1 edit (`POST /spotify-api/queue/remove`, with list+index+uri; returns 409 and refreshes if the queue has changed) and doesn't interrupt playback; auto items also have a `+` to promote them to manual.
- **Three buttons on each row of the favorite albums page** (same as the favorite artists page): play this album (`playAlbumsNow([id])`, via `play-albums`; tracks come from the favorites table cache, no Spotify call), shuffle this album (`play-albums` with an extra `shuffle_tracks` parameter: shuffle **all tracks** of the given albums together before queueing; for a single album that just shuffles its tracks), and unfavorite (star, `DELETE /spotify-api/favorites/<id>`, removed from the list on the spot — previously you had to open the album page and click the star). The shuffle button at the top keeps its meaning — shuffle the *order of albums*, with each album still in track order. The header order is now: Recently Played, Queue, favorite artists, favorite albums, favorite tracks, fullscreen, connect.
- **Isolation from the Spotify app (2026-10-05)**: `/me/player` is account-wide, not per device. Previously, while the Spotify app was playing, V1's queue driver carried on as usual: in the last 15 seconds it pushed the next V1 track into **the app's** play queue, when the app stopped it continued the V1 queue on **the app's device**, and autoplay used whatever the app was playing as its seed. Recently Played read the account's `/me/player/recently-played`, and the Queue page's Now Playing followed the app too. Now everything that belongs to V1 (the queue driver, autoplay seeds and top-ups, `reconcile_queue`, the Queue page's Now Playing, the "last playback" snapshot shown after a refresh) only acts when **the current playback device is V1 itself**. The web player registers as a Spotify Connect device under the fixed name `V1 Spotify Player` (frontend `new Spotify.Player({name})`, backend constant `V1_DEVICE_NAME` — the two must match), and `is_v1_device()` checks that name. **Recently Played is now recorded by V1 itself**: the `play_history` table gets one row whenever a poll (`now-playing` or the queue driver) sees the V1 device playing a new track (consecutive repeats of the same track aren't recorded twice); the most recent 200 are kept, the page shows the latest 50, and Spotify is no longer called. Recording started with this release, so earlier history is empty. **The bottom player bar is isolated too**: `now-playing` only returns live state when the current device is V1; while the app (or any other client) is playing, it takes the same fallback as "no active device" and returns V1's own last snapshot (paused, `live:false`), or nothing if V1 has never played (the player bar is hidden) — it no longer shows or controls the app's playback. Pressing Play at that point makes `togglePlayPause`'s slow path restart V1's track in the page at the saved position, and playback moves from the app to the web page (an account can only play on one device at a time). V1's "last snapshot" is stored in `app_settings['last_playback']` and survives restarts/deploys; polling happens every few seconds, so it is written immediately only when the track or the play/pause state changes, and otherwise the position is written every 15 seconds (pausing is itself a state change, so the resume position after a pause is accurate); it is deleted on disconnecting from Spotify (logout). The reverse direction can't be isolated: tracks played in V1 still show up in the Spotify app's own "recently played", which is an account-level Spotify record.
- **Header button selection state**: of the five entries Recently Played / Queue / favorite albums / favorite tracks / favorite artists, the one whose page is currently shown turns black (`.icon-btn.active`); pages with no corresponding button (search, artist page, album page) select none. All navigation (`goTo`/`goBack`/sync from another device/startup) goes through `renderDescriptor()`, and the selection is updated in one place there by `syncHeaderSelection()`.
- **How tracks hand off**: a background thread on the server, `queue_driver`, only works when the queue has content or autoplay is on. It sleeps according to the current track's remaining time (at most 5 seconds per sleep, so dragging the progress bar near the end is still caught; the seek/play/pause endpoints also wake it immediately), and only in the last 15 seconds hands the head of the queue to Spotify with `POST /me/player/queue` (native gapless handoff; it keeps playing with the page in the background or the screen locked, since it doesn't depend on browser JS), locking it in as `next` (it can no longer be removed, it is dequeued automatically once played, and a failed handoff to Spotify is rolled back). Fallback: if that window is missed (e.g. a very short track, or seeking to the end while the driver sleeps), single-track playback simply stops at the start/end; when the driver notices "it was playing last time, by the clock it should have finished, and now it's stopped at either end", it starts the head of the queue (`next` first) on the same device directly. A manual pause in the middle of a track doesn't trigger this. That's why every "play" is a single-track `uris:[track]` play (`POST /spotify-api/queue/play-track`, no longer with album context, so Spotify doesn't continue on its own); `play-album` plays the album's first track and puts the rest in the manual section; the Next button (`queue/next`) plays the head of V1's queue directly. Known: tracks that the old "+" pushed directly into Spotify's own queue aren't in V1's queue; they will play before the next handoff and can't be cleared from V1.
- **Media Session (lock screen / Control Center / headphone buttons)**: the page uses `navigator.mediaSession` to wire the system's play/pause/previous/next/seek to the same functions the page uses (`togglePlayPause(want)`/`skipPrevious`/`skipNext`/`seekToMs`), so Next on the lock screen also goes through V1's queue. Position comes from the SDK's `player_state_changed` (position/duration/paused, precise on this device) and is reported through `setPositionState`, falling back to server polling only when absent. **Per-track metadata/cover updates have been removed**: the Spotify SDK plays audio inside its own cross-origin iframe (titled "Spotify Embedded Player"), iOS attributes Now Playing to the iframe that is producing sound and re-takes it on every track change, seek and resume, and the page has no reliable way to override what it shows. (Tried: restarting the silent element at the moment of a track change; rewriting the cover, or removing and re-adding it; having the page download the cover as a data URL itself; pausing 0.6 s and resuming; restarting the silent element and rewriting metadata after seek/resume to reclaim the logo; explicitly setting `seekbackward`/`seekforward` to `null` to make the lock screen show previous/next instead of ±10 s — none worked, or the cost was too high: slower track changes, mid-song stalls, broken seeking.) **But not setting `mediaSession.metadata` at all (briefly tried 2026-09-19 to 2026-09-22) makes iOS stop treating the page as a proper background player, and playback is suspended outright when the screen locks** — not just wrong buttons. So a fixed identity is kept that is **set once and never touched again** (title "Spotify", artist "V1", no artwork), purely so iOS recognizes this as a media player, with no per-track updates. The lock-screen layout is still ±10 s skip rather than previous/next; this is confirmed to have no known solution and isn't being pursued further. The page still runs a looping silent `<audio>` (a 5-minute silent WAV generated at runtime, unlocked with play+pause in the first click, `play()` while Spotify is playing, `pause()` only after 15 s of pause), which keeps iOS from suspending the page between tracks (part of why the next track starts automatically). `?lockscreen=0` turns the silent element off (remembered; `?lockscreen=1` turns it back on), in case on some device it causes Spotify to be paused.
- Favorites (per album): `favorite_albums` table, `GET/PUT/DELETE /spotify-api/favorites(/<id>)`, plus `PUT .../genres` for manual genre tags (Spotify has essentially no album-level genre data, so you pick from a fixed list of 10 common genres). New favorites (albums or tracks) are tagged `Jazz` by default (`DEFAULT_FAVORITE_GENRES`, reflecting the author's taste and saving a manual tagging step), which can be changed or cleared right away. The `ON CONFLICT` update branch of `add_favorite`/`add_favorite_track` doesn't touch the `genres` column, so favoriting the same thing again (e.g. reopening the album page) doesn't reset your edited tags back to Jazz — even an emptied tag list is preserved. The album page has a star button; the star icon in the header opens the favorites list, which can be filtered with three dropdowns (Artist/Genre/Era) and has a sort dropdown: Year (default, newest → oldest, albums without a release date last), Recently added (by time favorited, newest → oldest), A–Z (album name, case-insensitive). The choice is remembered in the browser's localStorage (`spotify_fav_order`); sorting is purely client-side. Favorited albums are cached in this table together with their full track lists (the frontend uploads the already-loaded data when favoriting, no extra request). It is a separate table from `catalog_cache` above but has the same effect: opening a favorited album later makes zero Spotify requests. Favorites live on the server, so like the Spotify authorization they are naturally shared across devices.
- **Track favorites, fully independent of album favorites**: table `favorite_tracks` (id/uri/name/artists/image/album_id/album_name/release_date/duration_ms/genres/added_at), `GET/PUT/DELETE /spotify-api/favorite-tracks(/<id>)`, `PUT .../genres`. It is unrelated to `favorite_albums` — favoriting a track doesn't favorite its album, and vice versa. The icon is a heart (`ICON_HEART`) to distinguish it from the album star; `trackFavoriteButton(t, favorited)` is the shared favorite/unfavorite button (the album detail page, Recently Played, the fullscreen player bar and the Queue page's Now Playing all use the same logic). The Queue page's "Now Playing" comes from `handle_queue`'s `current` (built from the in-memory `_last_playback`, which originally had no `id`/`release_date`; added 2026-09-23: `id` is sliced from the end of the `uri`, `release_date` is carried over from `last_playback`); it only gets the favorite heart, not a "+" to queue (no point queueing what's already playing). A new header icon (heart) opens the "Favorite Tracks" list page with Artist/Genre/Era filters and Year/Recently added/A–Z sorting + direction — the same code as the favorite albums page (`sortFavorites`/`buildFilterSelect`/`eraOf`/`COMMON_GENRES`/`FAV_ORDERS`/`FAV_DEFAULT_DIRS` reused directly; only the state variables, localStorage keys (`spotify_trackfav_order`/`spotify_trackfav_dirs`) and API paths differ). The play button (▶) on the favorite tracks page uses it.
  - **Shuffle**: the favorite tracks page and the favorite albums page both have a separate shuffle button next to the existing play button (`ICON_SHUFFLE`, Fisher–Yates shuffle, without mutating the original array) — two buttons, not one button toggling modes. On the favorite albums page shuffle means "shuffle the order of these albums" (track order within each album is kept); on the favorite tracks page it means "shuffle the order of these tracks". The icon is two crossing diagonals with two arrowheads (similar to Spotify's official shuffle symbol). Fixed once on 2026-09-23: of the two hand-written diagonals, one was a true 45° (`l8 -8`) while the other had been written as `l8 7` (wrong slope, stopping just short of the arrow tip) — that was the one that looked "crooked" on a real device; changing it to `l8 8` makes the two strictly symmetric, each landing exactly on its arrow tip.
- **Artist favorites, independent of both album and track favorites**: table `favorite_artists` (id/name/image/genres/added_at), `GET/PUT/DELETE /spotify-api/favorite-artists(/<id>)`, `PUT .../genres`. A person icon in the header (the 7th; `.header-right` gained `flex-wrap`, and the gap shrinks to 6px at ≤420px, so on narrow screens it wraps instead of overflowing) opens the list page; a person button next to the artist page title favorites/unfavorites. The avatar is the artist's own image: `GET /artists/{id}` (available in Dev Mode; returns `images`, without genres/popularity) is cached permanently by `fetch_artist_meta()`, and `pick_artist_image()` picks "the smallest image at least 160px wide" (the list only shows about 40px; no need for the 1000px original). On favoriting, the server's `refresh_artist_image()` swaps in the real avatar directly; the latest album cover sent by the client is only a fallback (used if Spotify errors or the quota is exhausted). **Artists favorited earlier** still had an album cover stored; `backfill_artist_images()` in `list_favorite_artists()` fills them in concurrently and **waits for them (up to 4 seconds) before returning**, so the list page already shows real avatars when it opens, rather than "next time" (each artist is tried only once per process, so failures aren't retried on every list refresh; once successful it's cached permanently and never requested again). **The artist page** (the artist's albums page) also shows this avatar before the title: the response of `GET /spotify-api/artists/<id>/albums` now includes `artist_image` (same permanent cache; null if unavailable, and the page renders as usual); without an avatar it falls back to the latest album cover for favoriting. Avatars on the artist page and in the favorites list both go through `coverImg()` and are **controlled by the covers toggle at the far right of the search bar** — when it's off, none are shown. The list page has Genre / Era filters and Year / Recently added / A–Z sorting (+ direction, default Year, consistent with the other two favorites pages), with no Artist filter (each row is one artist); new favorites default to Jazz, same rule as albums/tracks. **An artist's Year/Era = the release date of their earliest album** ("active since", shown in the row as "since 1958"): `favorite_artists.first_release_date`, computed by the artist page from the already-loaded album list and saved along with the favorite (`earliestRelease()`: the smallest `release_date`, ignoring placeholder/dirty data before 1900), with no extra Spotify call; the API calls it `release_date` so that `sortFavorites`/`eraOf` work across all three favorites pages. **Artists favorited before this feature have no date** (the column added by `ALTER TABLE` is empty, landing in "Unknown era"); opening their artist page once fills it in automatically (`loadArtist` notices a favorited artist without a date and silently PUTs once). An existing date isn't cleared by favoriting again, and is replaced if an earlier one is computed. Limitation: an artist's album list fetches at most 200 albums (`fetch_artist_albums`), so for artists with more, the earliest one may not be seen.
  - **"Play artist" = play the music you've favorited that belongs to this artist**, all from local data with zero Spotify requests: `favorite_track_pools()` groups the tracks cached in favorited albums plus favorited tracks (not duplicating those already in a favorited album) under each artist **name** (these two tables store names, not ids, so different artists with the same name get mixed together — a known limitation), ordered within each artist by release date from earliest to latest, and by track number within an album. Each list row shows the size of that pool (0 shows "no favorite tracks yet").
  - **Playing just one artist**: each row on the favorite artists page has its own play button (black) and shuffle button, sending the same `play-artists` with only this artist in `artist_ids` (shuffle shuffles this artist's tracks). For artists without favorite tracks both buttons are disabled (greyed out, with a "has no favorite tracks yet" hover hint). The pair of buttons at the top still plays/shuffles "the whole currently filtered list".
  - **In-order play**, `POST /spotify-api/queue/play-artists {artist_ids, shuffle:false, device_id}`: in list order, one artist finishes before the next starts; a track belonging to several artists (a collaboration) is queued only once, credited to the one earlier in the list; artists without favorite tracks are skipped with a "N without favorites skipped" hint; 404 if none have any. **Shuffle** (`shuffle:true`): each artist's tracks are shuffled separately, then it goes round by round, drawing 1 track from each artist and reshuffling the artist order every round, until everything is drawn — an artist with 300 favorited tracks doesn't drown out one with only 3, the same idea as auto mix's interleaving of multiple seeds. It also replaces the existing manual/auto queue, capped at 1000 tracks. `replace_queue_and_play()` is now a module-level function shared by `play-tracks` and `play-artists`.
- **Sort direction for favorites lists**: an arrow button next to the sort dropdown toggles ascending/descending (ascending = smallest first: earliest year / earliest favorited / A→Z; descending is the reverse). The icon is a fixed vertical line with an arrowhead at each end (`ICON_SORT_UPDOWN`); ascending and descending **use the same icon**, with no change of glyph, and the current state shows only in the hover text. Changed on 2026-09-23 from "swap between two icons": that version was reported to render the two states inconsistently, so both states now always use the same icon, eliminating the problem at the root. Each sort remembers its own direction (defaults: Year and Recently added descending, A–Z ascending), stored in localStorage (`spotify_fav_dirs`); albums without a release date always sort last regardless of direction, with ties broken by album name.
- **Playing the whole filtered favorites list**: the black play button next to the filter/sort controls on the favorites list plays all albums in the current list in display order (current filter + sort + direction): `POST /spotify-api/queue/play-albums {album_ids, device_id}`; the first track plays immediately and everything else goes into the manual queue. Tracks come straight from the favorites table cache (no Spotify call); only uncached ones are fetched. At most 300 albums and 1000 tracks (`PLAY_ALBUMS_MAX_*`); beyond that a hint says only the first N tracks were queued.
- **Both "play as queue" entries replace the queue**: the album page's Play album and the play button above both clear the old manual and auto sections first and then insert the new queue (`q["manual"] = new tracks; q["auto"] = []`), after which `refresh_auto` recomputes auto from the new queue (if Auto up next is on). Single-track play and "+" add-to-queue are unchanged (they don't clear the queue).
- **Direct play clears the stale `next`**: `start_track()` (shared by single-track play, Play album and "play favorites") and `/spotify-api/player/play` (the raw play used by Recently Played rows and the dedup list, bypassing V1's queue) now clear `q["next"]` after actually calling `PUT /me/player/play`. Before 2026-09-22 they didn't, so an interrupted, unfinished track got stuck in `next` and stayed at the top of Up Next (that row has no × button, so it couldn't be removed), even though on Spotify's side that "next track" had already been replaced by the new play command — only V1's stale record was stuck. "Really starting something new" is distinguished from "resuming the same track after a page refresh": in the latter case `togglePlayPause` passes `position_ms`, and `next` is not cleared (the originally queued track is still valid). Clearing the queue (trash button) is a separate path that doesn't go through this, and `next` is kept by design (Spotify offers no way to retract it, so that track will still play after the first track of the new queue).
- **Clearing the queue**: the trash button next to the Up Next heading on the queue page (with a confirmation dialog), `POST /spotify-api/queue/clear`, empties manual and auto, likewise keeping the `next` already handed to Spotify. After clearing, the currently playing track is marked as "handled" (`auto_tried` and `_topup_key`), so even with Auto up next on, the queue doesn't refill right away; playback stops after this track, and to continue you can toggle Auto up next off and on again.
- **Artists on the album page are clickable**: each artist name under the album detail page title is a link to that artist's albums page (`artist_ids` come from the album metadata; for favorited albums served from the favorites table cache, the ids come from the permanently cached `album_meta`, costing one extra Spotify request the first time).
- Navigation is a real back stack (Search → Artist → Album → Dedup, push/pop level by level) rather than always jumping back to search. The same descriptor structure also drives cross-device "content sync": forward navigation pushes to `/spotify-api/view-state`, and updates from other devices are rendered with the same `renderDescriptor()`. The view state is stored in `app_settings.view_state` (survives service restarts); the page always renders on startup, showing the home page (Recently Played) when no view is saved. Previously the state lived only in memory and was empty after every deploy/restart, while the startup logic only rendered when there was a saved view, leaving the home page blank.
- **Fullscreen mode**: a fullscreen button in the header (four-corners icon) enters it: search, lists and other buttons are hidden, leaving only the current track's player bar, centered and enlarged — cover (or logo), title/artist, progress bar, Prev/Play/Next, volume. The button turns black while on; click again to exit. The cover follows the "show covers" toggle; with covers off (or no cover for the track), the Spotify logo is shown instead. Layout is pure CSS (`body.fs`, with the player bar's rows flattened and rearranged via `display:contents`); in browsers that support it, real browser fullscreen is requested as well (not available to pages on iPhone, which get only the CSS fullscreen), and exiting browser fullscreen with Esc also exits the mode. It won't enter when nothing is playing. Not persisted; a refresh returns to the normal view.
- All page copy is in English; the header dropped the Media/Home links, and the login status is tucked into a line of small text at the top right (the big button only appears when not connected). Search and "show covers" are minimal line-icon buttons; the "show covers" state is still stored in localStorage and restored on the next visit.
- **Dark mode**: click the Spotify icon at the top left of the header to toggle; remembered in `localStorage` (`spotify_dark`). Rather than drawing a separate dark palette, the page content is literally inverted black-for-white: `invert(1)` flips every pixel's lightness and hue, and `hue-rotate(180deg)` turns the hue back (so the only non-monochrome color, the red of `.error`, stays red instead of turning cyan). This avoids hunting down the dozens of `#fff`/`#000`/`#999`/`#eee` values in what is already a pure black-and-white line-art page and maintaining a second dark set. Real images such as album covers and artist avatars (`.cover`) get the same filter again to cancel it out, so covers show their true colors in dark mode instead of a color-inverted "negative". A small blocking script at the very top of `<head>` reads localStorage and sets `class="dark"` before CSS takes effect, avoiding a flash of the light theme on refresh.
  - **Where the filter goes**: not on `html`, but separately on `#app` (a new wrapper around the search panel and `#view`), `header` and `#nowplaying` (the player bar) — for two reasons. ① `#nowplaying` is `position:fixed`, and CSS specifies that once an ancestor has a `filter`, `fixed` descendants are positioned relative to that ancestor instead of the real viewport; it happened to work with the filter on `html` only because `html`'s box roughly equals the viewport, which isn't a guarantee to rely on, so splitting it is more robust. ② When trying to hard-code `background:#000` on `html`/`body` to cover the "status bar / overscroll" background described below, it turned out this black was flipped again by the same ancestor's `filter:invert` back to white (seen in screenshots), turning the body background white as well. With the `filter` applied only to the content elements, `html`/`body`'s own `background` is no longer affected and can simply state the real black/white.
  - **Notch/status bar and pull-to-refresh overscroll**: both lie outside the page content's boxes, and the browser fills them directly from the *real* background color of `html`/`body` (not the filtered result), which is why "no filter on html" above is a prerequisite. `viewport-fit=cover` extends the page into the safe areas, and `body`'s padding is written as `max(20px, env(safe-area-inset-top))` and so on, so the space freed around the notch is filled by `body`'s real background (true black in dark mode); `#nowplaying`'s left/right/bottom padding also uses `env(safe-area-inset-*)` so the Home indicator doesn't cover it. `<meta name="theme-color">` was also added (switching to `#000000` in dark mode, for browsers that use it to color their own address bar/toolbar), plus `apple-mobile-web-app-status-bar-style` (only effective in "Add to Home Screen" standalone mode; a no-op in a normal Safari tab).
  - **What can't be verified locally**: these (notch coverage, overscroll color, status bar style) are native iOS Safari rendering behaviors that headless Chrome can't reproduce; only code reasoning plus screenshots verify that the page itself hasn't regressed (background values and `#nowplaying` position identical before and after toggling). Whether it's really fixed on a device has to be checked on the device.
  - **Bug: the exit button ended up off-screen in fullscreen mode (fixed 2026-10-05)**: `body.fs header` makes `header` `position:fixed` in fullscreen, but `header` was still inside the filtered `#app` — the same "a filtered ancestor changes the containing block of fixed elements" rule, this time misplacing the exit-fullscreen button instead of `#nowplaying`. More subtly, `body`/`html` had never reset the default user-agent margin (Chrome/Safari give `body` an 8px margin by default), so `#app` (along with the `header` that no longer belonged in it) was offset a further 8px from the real viewport; in screenshots the exit button sat entirely beyond the right edge of the visible area, unreachable and invisible. Fix: move `header` out of `#app` to be a direct child of `body` like `#nowplaying` (with its own `filter` so it's still inverted in dark mode), add `margin:0` to `html, body`, and change the fullscreen padding of `header` and `#nowplaying` to `max(original px, env(safe-area-inset-*))` so the notch/Home indicator doesn't cover them. The exit button's actual coordinates in fullscreen + dark mode were measured in a headless browser to confirm it lands inside the viewport.
  - **Fullscreen notch stayed white — five attempts to find the real cause (2026-10-05)**: iOS 26 Safari **no longer reads `theme-color`**; it colors the status bar and bottom toolbar from the CSS `background-color` **property value** of a `position:fixed` element touching the top/bottom edge of the screen — it reads the property value, not the filtered pixels. The home page has no fixed element at the top, so Safari takes `body`'s real background (true black in dark mode) and it's fine; in fullscreen, `#nowplaying` covers the whole screen and touches the top edge, and it was relying on `filter:invert` to turn a literal `#fff` background into black, so Safari read `#fff` and the notch was white. **Fix**: `#nowplaying` no longer has a filter itself; in dark mode its background is written as true black directly (with a white `border-top`), and the filter moves to its content (`.progress-row` and `.main-row > *` — in fullscreen `.main-row` is `display:contents` and has no box of its own, so the filter has to go on its children). Covers used to need a second inversion to cancel the parent's filter; now that the parent has no filter, covers aren't filtered (`#npCover { filter:none }`). This also fixes the same kind of issue where the bottom toolbar could be tinted white in normal mode.
    - **Wrong turns taken earlier, recorded so they aren't repeated**: ① changing the player bar's `top` to `env(safe-area-inset-top)` so that `body`'s background would show through — no effect; Safari doesn't look at which pixels are exposed at all. ② adding a `#notchBackdrop` shown only in fullscreen to cover the notch — no effect; in a normal Safari tab `env(safe-area-inset-top)` is 0, so that layer had zero height (removed). ③ assuming `requestFullscreen()` had put the page into system-level fullscreen — wrong; on iPhone this API isn't available for ordinary elements in the first place, removing it changed nothing, and it has been restored (it still enters real fullscreen on desktop/iPad). Lesson: headless Chrome can't reproduce iOS Safari's status-bar color rules; for this kind of problem, check the current Safari version's actual behavior first instead of trying CSS blindly.
- **Known iOS limitations**: when the browser tab is in the background or the screen is locked, iOS Safari strictly suspends web-page JS execution. This is a platform limitation, not a bug in this service; a web page can't guarantee background/lock-screen continuous playback as reliable as the native Spotify app, so test the actual behavior on a real device. Desktop browsers don't have this limitation.
