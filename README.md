# v1-spotify

V1 上的 Spotify 网页播放控制服务（`https://spotify.example.com/spotify`）：单文件 Python 服务（标准库 `ThreadingHTTPServer`，前端页面内嵌在 `SPOTIFY_PAGE` 里），浏览器标签页通过 Web Playback SDK 注册成一台 Spotify Connect 设备，V1 负责 OAuth、Web API 代理、自己的播放队列和收藏。

从 [`V1-web-services-deployment`](../V1-web-services-deployment) 拆出来（`git filter-repo`，保留了这三个文件的完整提交历史）。

## 文件

| 文件 | 作用 | V1 上的位置 |
|---|---|---|
| `spotify-server.py` | 服务本体（后端 + 内嵌前端） | `/opt/spotify/server.py` |
| `spotify-server.service` | systemd 单元（`127.0.0.1:8793`） | `/etc/systemd/system/spotify-server.service` |
| `spotify-server.env.example` | 密钥模板，复制成 `/opt/spotify/spotify.env`（root 0600）后填 `SPOTIFY_CLIENT_ID`/`SPOTIFY_CLIENT_SECRET` | `/opt/spotify/spotify.env` |
| `Caddyfile.snippet` | Caddy 里 `/spotify` 和 `/spotify-api/*` 两条路由（走 `forward_auth 127.0.0.1:8800 /auth/check`） | 合并进 `/etc/caddy/Caddyfile` |

数据（OAuth 令牌、队列、收藏、目录缓存）在 V1 的 sqlite `/opt/spotify/tokens.db`，不在仓库里。

## 部署（独立于原仓库时）

```bash
scp spotify-server.py root@YOUR_SERVER:/opt/spotify/server.py
scp spotify-server.service root@YOUR_SERVER:/etc/systemd/system/spotify-server.service
ssh root@YOUR_SERVER 'python3 -m py_compile /opt/spotify/server.py && systemctl daemon-reload && systemctl restart spotify-server && systemctl is-active spotify-server'
```

注意：**目前 V1 线上仍由 `V1-web-services-deployment` 的 `deploy.sh` 部署**（它会把那边仓库里的 `spotify-server.py` 装到 `/opt/spotify/server.py`）。两边同时改会互相覆盖——要以这个仓库为准，需要先把原仓库里的 Spotify 文件和 `deploy.sh` 里对应的几行去掉。

## 本地运行

```bash
SPOTIFY_CLIENT_ID=... SPOTIFY_CLIENT_SECRET=... \
SPOTIFY_DB=./tokens.db SPOTIFY_PORT=8793 \
SPOTIFY_REDIRECT_URI=http://127.0.0.1:8793/spotify-api/callback \
python3 spotify-server.py
```

（Spotify 开发者后台的 Redirect URI 需要加上对应地址。）

## 说明（原 README 的 Spotify 章节）

独立服务 `spotify-server.service`（`127.0.0.1:8793`），Caddy 通过 `/spotify` 和 `/spotify-api/*` 两条已鉴权路由（同一 `forward_auth /auth/check`）转发，无需新 DNS。V1 只做 OAuth 令牌管理、Spotify Web API 搜索/浏览代理和播放控制代理；音频和封面字节不经过 V1，由浏览器里的 Spotify Web Playback SDK 直接和 Spotify 通信——这个浏览器标签页本身会注册成一台 Spotify Connect 设备（"V1 Spotify Player"）。

- **前提**：Spotify Premium 账号（免费账号的播放控制端点会 403）。首次使用需要在 `https://spotify.example.com/spotify` 点 "Connect Spotify" 走一次 OAuth 授权；没有单独的 "Enable Playback" 步骤，Web Playback SDK 的 `connect()`/`activateElement()` 会延迟到你点的第一个播放按钮内部同步触发，满足 iOS/Safari 要求播放解锁必须发生在真实点击手势里的限制。`ensureDevice()` 始终优先把播放指令发到*这个浏览器自己*的 SDK 设备（必要时先等最多 15 秒让它连上，2026-09-22 从 12 秒调大），而不是随便找一个已激活设备，所以在哪个设备点播放，声音就从哪个设备出。等到期后不再只问一次 `/spotify-api/devices` 就报"没有可用设备"——Spotify 自己的设备列表可能比这个连接实际就绪晚一拍才更新，改成再轮询最多 4 次（每次间隔 1.5 秒，期间弹一个 "Connecting to Spotify…" 的提示）才真的报错；`sdk.scdn.co` 脚本本身还没加载完导致 `connect()` 压根没被触发的情况也会在这里再给一次机会。之前遇到过这个提示是误报（脚本还在加载/连接还没就绪那几秒被撞上），2026-09-22 改的。
- 只持久化 `refresh_token`（存于 `/opt/spotify/tokens.db`），`access_token` 只在内存缓存，快过期时用 `refresh_token` 静默换新；Spotify App 的 `client_id`/`client_secret` 由 `/opt/spotify/spotify.env`（不入库）注入，和 `files-server.service` 里的 `FILE_API_TOKEN` 同等对待，不要把它们单独贴到别处。
- **搜索框回车 = 最相关搜索**：三个搜索图标（Artist/Album/Track）是显式选类型；键盘上的回车/Search 键不重复上次点过的类型，而是打 `GET /spotify-api/search/best`——一次 Spotify 请求里用逗号分隔的 `type=artist,album,track` 同时查三种类型（成本和单类型搜索一样，不是 3 倍），谁的最高结果和查询词完全一致（忽略大小写/首尾空格）就用谁，都不完全匹配则退回 Artist（和以前一路回车都是 Artist 的效果一样）。Spotify 本身不提供跨类型的相关度分数，这是能做到的最接近"最相关"的近似。
- 搜索以艺人/专辑为维度：- 搜索以艺人/专辑为维度：艺人页面按 Album/Single/Compilation 分组列出专辑；"Build deduplicated track list" 用归一化曲名分组去重（专辑类型优先：studio album > single > compilation > appears_on，同类型内选发行日期最早的版本，即偏向原始录音室版本而非后来的 Remaster/Live/Deluxe 重发），并保留可展开的其它版本供手动改选——这不是精确匹配，只是"简单去重"。曾经想用 Spotify 的 track `popularity` 字段做打分，但这个 Development Mode App 现在完全拿不到 popularity（单曲和批量端点都不返回该字段），所以已去掉这个维度，纯按专辑类型 + 发行日期排序。
- **Spotify 平台限制（2026-09-18 验证）**：这个 App 的每个分页端点（search、artist albums、album tracks）`limit` 参数硬顶在 10，超过 10（哪怕是文档写的合法值如 20、50）会返回 `{"error":{"status":400,"message":"Invalid limit"}}`；批量端点 `/v1/tracks?ids=...` 直接 403 Forbidden，单曲 `/v1/tracks/{id}` 可用但不再带 `popularity` 字段。更严重的是 `/v1/artists/{id}/albums` 有独立的**按天配额**（`QUOTA_EXCEEDED`，429，`retry-after` 实测约 20 小时），2026-09-18 当天就因为反复浏览/测试艺人页被打满过一次，期间艺人页完全不可用，搜索和播放控制不受影响（配额是分端点算的，不是整个 App 被封）。这些都不是本服务的 bug，是 Spotify 对未获扩展配额的 Development Mode App 的限制；`spotify-server.py` 里 `SPOTIFY_PAGE_LIMIT=10` 常量已按实测结果调整，"Build deduplicated track list" 因为单个请求成本很高（一个艺人的每张专辑都要单独查 tracks）已经从艺人页隐藏（后端接口和代码都还在，只是入口不显示）。如果以后 App 升级到扩展配额，可以放宽 `SPOTIFY_PAGE_LIMIT` 并把去重按钮加回来。
- **永久目录缓存**：为应对上面的按天配额，`tokens.db` 新增 `catalog_cache` 表（`cache_key`/`payload`/`cached_at`，无过期时间），`fetch_artist_albums`、`fetch_album_tracks`、`fetch_album_meta` 都是先查这张表，查不到才打 Spotify。艺人的完整专辑列表、每张专辑的元数据和曲目，只要被请求过一次，之后永远从 sqlite 读，不会再消耗配额（实测：冷启动一次真实请求 0.3s，命中缓存 0.02s）。这个缓存目前没有失效/清理机制，艺人发新专辑不会自动出现，需要手动清空对应 `cache_key`（当前没有做管理界面，需要直接操作 sqlite）。
- 播放控制（next/previous/volume/seek）统一走 `/spotify-api/player/*`；**播放/暂停走 SDK 本地**（`togglePlayPause` → `state.player.pause()/resume()`）：以前是 取 device → GET now-playing → PUT pause → 再 GET now-playing 四步串行，V1 每次调 Spotify 约 0.3 秒，点一下要 1 秒以上才有反应。刚重载页面、SDK 还没有状态时走 Web API 慢路径。`?fastplay=0` 可切回慢路径（会记住，`?fastplay=1` 再打开），用来对比。静音元素的"解锁"（play+pause）只在它还没真正播放过时做，不再每次点击都做——否则它正好撞在 SDK 恢复播放的瞬间。
  - **一次只允许一个动作**（`playPauseBusy` 锁）：点了 play，按钮立刻 disable，点第二下（不管是再点、点 pause、还是锁屏/耳机按键触发的）直接被忽略，什么都不做，直到这次 play 真正落地（SDK 的 `resume()`/`pause()` Promise resolve）才解锁、按钮才重新可点；此时点 pause 才会真的执行。2026-09-23 之前的版本：点击立刻乐观翻转图标，2 秒后再单独校验一次、必要时用 Web API 补发一次指令，还有一个额外的"3 秒内相信自己点击结果、忽略轮询"的窗口（`localPlayIntent`）——这几层叠在一起，快速连续点击时经常出现图标翻回去、暂停变成重新播放之类的错乱。现在全部删掉：一次点击只对应一次指令、一次状态更新，SDK 失败才退回 Web API 单独试一次，不再有背景定时器或"相信自己"的窗口。离线测试覆盖了：连点两下只发一次指令、点击方向相反时后一下被直接忽略、连续三次同步点击只生效一次、SDK 和 Web API 两条路径分别验证。播放条含真正的拖动 seek（不再是只读进度条），进度条放在播放条最上面一行，避免在 iOS 上贴着屏幕底部边缘拖动时被系统的滑动手势抢走。页头新增 Recently Played（时钟图标）和 Play Queue（列表图标）两个入口，都在收藏星标左边；`GET /spotify-api/recently-played`、`GET /spotify-api/player/queue`、`POST /spotify-api/player/queue`（加入队列不打断当前播放）都需要 `user-read-recently-played` scope，2026-09-18 加的，之前授权的账号需要断开重连一次。
- 播放连续性：点专辑里任意一首歌会从那首开始播放整张专辑（用 `context_uri` + `offset`），而不是放完一首就停，Spotify 自己会在这个 context 内接着放同专辑剩下的曲目。跨专辑的自动连播不再要求"必须从艺人页浏览进入"：`advanceAlbumQueue()` 优先用已知的 `state.albumQueue`（从艺人页某个分组点进来时才有），没有的话会懒加载查一次 `GET /spotify-api/albums/<id>/next-in-artist`——这个懒加载查询本身也走上面的永久缓存，冷启动最多打一次 `artists/{id}/albums`（单页 10 条，不是完整分页），之后同一个艺人+专辑类型永远免费。去重列表的单曲点击/"Play all" 用的是裸 `uris` 队列，会清空 `state.albumQueue`，和专辑的 auto-advance 是两套互不干扰的机制。
- **Queue（V1 自己维护，不读 Spotify 的队列）**：Spotify Web API 只能往队列里加，没有移除/清空接口，也分不出手动和自动，所以队列完全由 V1 持有：`tokens.db` 的 `app_settings` 里 `queue`（JSON：`manual` 手动区、`auto` 自动区、`next` 已交给 Spotify 的那一首）和 `autoplay`（**默认关**）。手动区永远排在自动区前面，两者的分界就是页面上的边界线，每项带 `manual`/`auto` 标签。`+` 只是往 V1 的手动区追加（`POST /spotify-api/queue/add`）；如果这首本来就在自动区，就从自动区挪到手动区末尾（标签由 auto 变 manual）。自动续播开关（`PUT /spotify-api/queue-settings`）：开 → 自动区是"最后几个手动项的 mix"：取手动区最后 4 张不同专辑（不够再补 `next`，手动区为空则用当前歌）作为种子，每个种子先给出该专辑里它之后的曲目、再依次是同艺人后面的专辑（同类型，新到旧）：至少走 3 张（`AUTO_ALBUMS_PER_SEED`），不够 12 首（`AUTO_SEED_TRACK_TARGET`）就继续往前走，最多到 10 张（`AUTO_ALBUMS_PER_SEED_MAX`）为止——单曲艺人（一张"专辑"就 1 首歌）按固定 3 张走只够 3 首，2026-09-22 从"固定 3 张"改成"3 张打底、不够再往前找到凑够或到安全上限"，同一个艺人发行大量单曲时不会刚起步就停手；全部走完（`find_next_album_for_artist` 返回 None，即这个艺人这个类型确实没有更早的了）会提前停止，这时候数量少是真的没素材了，不是 bug。几路种子按每轮 6 首轮流穿插（`AUTO_CHUNK`，只影响多个种子交替时每张专辑连续出现几首，单种子时本来就是把能拿到的全部取完，这个数字不影响总数；2026-09-22 从 3 调到 6，让单张专辑在列表里显得更成片）（最新的种子排最前），去掉已在手动区/`next` 的歌，总量上限 30 首（`AUTO_CAP`）。下一张专辑的查找按页懒加载（每页 10 条、每页永久缓存，最多 12 页，即冷缓存每个艺人+类型最多 12 次 `artists/{id}/albums`（曾设成 5 页，Joe Pass 这种一百多张专辑的艺人，1974 年的老专辑在很靠后的页里，翻不到就找不到"下一张"，自动区只剩本专辑剩余曲目）），专辑不在已取页里时按发行日期回退，不再只看最新 10 张；关 → 只清空自动区，手动区不动。开着的时候：①自动区随播放被消耗，driver 在每首新歌开始时若它少于 15 首（`AUTO_LOW`）就补回到最多 30 首（每首歌只补一次，后台线程，不阻塞交接）；②增删手动项会立刻按新的"最后几个手动项"重算；③手动区和自动区都放完了，会在最后 15 秒以当前歌重新算一批；④你在自动区点 × 删掉的歌记在 `auto_removed`（最近 200 首），补充/重算时不会再放回来。每项的 × 是纯 V1 编辑（`POST /spotify-api/queue/remove`，带 list+index+uri，队列已变则 409 并刷新），不会打断播放；自动区每项还有 `+` 可提升为手动。
- **专辑收藏页每一行的三个按钮**（和艺人收藏页一致）：播放这张专辑（`playAlbumsNow([id])`，走 `play-albums`，曲目取自收藏表缓存，不调 Spotify）、随机播放这张专辑（`play-albums` 多了个 `shuffle_tracks` 参数：把所给专辑的**所有曲目**一起洗牌再排队；单张专辑就是把它的曲目打乱）、取消收藏（星，`DELETE /spotify-api/favorites/<id>`，当场从列表移除，以前只能进专辑页点星）。顶部那个随机播放键的含义不变——打乱"专辑的顺序"，每张专辑内部仍按曲序。页头顺序现在是：Recently Played、Queue、艺人收藏、专辑收藏、单曲收藏、全屏、连接。
- **和 Spotify App 隔离（2026-10-05）**：`/me/player` 是账号级的，不分设备——以前 App 在放歌时，V1 的队列驱动会照常工作：最后 15 秒把 V1 队列的下一首推进 **App 的**播放队列、App 停下时把 V1 队列接着放到 **App 那台设备**上、自动续播拿 App 正在放的歌当种子；Recently Played 读的是账号的 `/me/player/recently-played`，Queue 页的 Now Playing 也跟着 App 走。现在凡是 V1 自己的东西（队列驱动、自动续播的种子和补歌、`reconcile_queue`、Queue 页的 Now Playing、刷新后的"最后一次播放"快照）都只在**当前播放设备是 V1 自己**时才动：网页播放器注册成 Spotify Connect 设备时用固定名字 `V1 Spotify Player`（前端 `new Spotify.Player({name})`，后端常量 `V1_DEVICE_NAME`，两边必须一致），`is_v1_device()` 按这个名字判断。**Recently Played 改成 V1 自己记**：`play_history` 表，每次轮询（`now-playing` 和队列驱动）看到 V1 设备在放一首新歌就记一条（连续同一首不重复记），保留最近 200 条，页面取最近 50 条，不再调 Spotify。从这次上线开始记，之前的历史是空的。**底部播放条也隔离**：`now-playing` 只有在当前设备是 V1 时才返回实时状态；App（或任何其它客户端）在放时，走和"没有活跃设备"同一条退路，返回 V1 自己上一次的快照（暂停、`live:false`），V1 从没放过就是空（播放条隐藏）——不会再显示或控制 App 的播放。这时按 Play，`togglePlayPause` 的慢路径会把 V1 那首歌按保存的进度在网页上重新放起来，播放随之从 App 转到网页（一个账号同一时间只有一台设备出声）。注意 V1 的"最后一次快照"只存在内存里，服务重启后为空。反方向隔离不了：V1 播过的歌依然会出现在 Spotify App 自己的"最近播放"里，那是 Spotify 账号级记录。
- **页头按钮的选中状态**：Recently Played / Queue / 专辑收藏 / 单曲收藏 / 艺人收藏 五个入口，当前显示的就是哪个页面，对应按钮变黑（`.icon-btn.active`）；搜索、艺人页、专辑页这些没有对应按钮的页面则都不选。所有导航（`goTo`/`goBack`/别的设备同步过来/启动）都经过 `renderDescriptor()`，选中状态就统一在那里的 `syncHeaderSelection()` 更新。
- **播放如何衔接**：服务端有个后台线程 `queue_driver`，只在有队列内容/自动续播开着时工作，按当前歌剩余时间休眠（单次最多睡 5 秒，这样拖动进度条到临近结尾也来得及；seek/播放/暂停接口也会立刻唤醒它），进入最后 15 秒才把队首那一首用 `POST /me/player/queue` 交给 Spotify（原生无缝衔接，页面在后台/锁屏也照常放，因为不依赖浏览器 JS），并把它锁定成 `next`（此后不能再删，播放后自动出队，交给 Spotify 失败会回滚）。兜底：如果错过了这个窗口（例如很短的曲目、或睡眠期间拖到结尾），单曲播放会直接停在开头/结尾，driver 发现"上次看到它在播、按时间已该放完、现在停在两端"时，会直接在同一设备上开始队首（`next` 优先），手动暂停在曲目中间不会触发。所以所有"播放"都是单曲 `uris:[track]` 播放（`POST /spotify-api/queue/play-track`，不再带专辑上下文，避免 Spotify 自己接着放）；`play-album` 把专辑第 1 首放出来、其余放进手动区；Next 键（`queue/next`）直接播 V1 队首。已知：此前通过旧版 "+" 直接塞进 Spotify 自己队列里的歌不在 V1 队列中，会在下一次衔接前先放掉，无法从 V1 清除。
- **Media Session（锁屏/控制中心/耳机按键）**：页面用 `navigator.mediaSession` 把系统的 play/pause/上一首/下一首/拖动进度接到页面同一套函数（`togglePlayPause(want)`/`skipPrevious`/`skipNext`/`seekToMs`），所以锁屏上的 Next 同样走 V1 队列；进度用 SDK 的 `player_state_changed`（position/duration/paused，本机精确）通过 `setPositionState` 上报，没有才退回服务端轮询。**逐首更新元数据/换封面的逻辑已经删除**：Spotify SDK 在自己的跨域 iframe（标题 "Spotify Embedded Player"）里出声，iOS 把 Now Playing 归给正在出声的 iframe，换歌、seek、恢复时都会重新接管，页面没有办法稳定改掉它显示的内容（试过：换歌瞬间重启静音元素、重写/去掉再放回封面、页面自己下载封面成 data URL、暂停 0.6 秒再恢复、seek/恢复后重启静音元素并重写元数据夺回 logo、显式把 `seekbackward`/`seekforward` 设成 `null` 想让锁屏显示上一首/下一首而不是 ±10s——都无效，或者代价太大（换歌变慢、歌曲中途停顿、seek 出问题）。**但完全不设置 `mediaSession.metadata`（2026-09-19 到 2026-09-22 短暂试过）会让 iOS 不把这个页面当成正经的后台播放器，锁屏时playback 直接被挂起**，不只是按钮显示错——所以留着一个**只设置一次、之后再也不碰**的固定身份（标题 "Spotify"、artist "V1"、没有封面图），纯粹是为了让 iOS 认这是个媒体播放器，不涉及任何逐首更新。锁屏按钮布局目前仍是 ±10s 快进快退而不是上一首/下一首，这个已确认没有已知解法，不再折腾。页面自己仍然放一个循环的无声 `<audio>`（运行时生成的 5 分钟静音 WAV，第一次点击里 play+pause 解锁，Spotify 在播就 `play()`，暂停 15 秒后才 `pause()`），作用是让 iOS 在换歌间隙不挂起页面（"下一首能自动接上"的一部分原因）。`?lockscreen=0` 可关掉无声元素（会记住，`?lockscreen=1` 再打开），前提是某台设备上它会让 Spotify 被暂停。

  - **专辑详情页**：每首歌旁边一个独立收藏按钮，进页面时 `Promise.all` 并发查这张专辑所有曲目的收藏状态（全是本地 sqlite 查询不摸 Spotify，放心并发）。

- **深色模式**：点页头左上角那个 Spotify 图标切换，`localStorage`（`spotify_dark`）记住。不是另画一套深色配色，是把页面内容literal地黑白颠倒：`invert(1)` 把每个像素的亮度和色相都翻过来，`hue-rotate(180deg)` 再把色相转回去（这样唯一一处非黑白的颜色，`.error` 的红色，翻转后还是红色，不会变成青色），省得把这个本来就是纯黑白线条风格的页面里几十处 `#fff`/`#000`/`#999`/`#eee` 一个个找出来再配一套深色值。专辑封面、艺人头像这些真实图片（`.cover`）会再套一层同样的 filter 抵消掉，所以深色模式下封面显示真实颜色，不会变成色彩反相的"底片"效果。`<head>` 最前面有一段阻塞式的小脚本，在 CSS 生效前就读 localStorage 并打上 `class="dark"`，避免刷新时先闪一下浅色再变深色。
  - **filter 加在哪**：不是 `html`，是 `#app`（包住 header/搜索面板/`#view` 的新 wrapper）和 `#nowplaying`（播放条）各自单独套一份——两个原因。① `#nowplaying` 是 `position:fixed`，CSS 规定祖先元素一旦有 `filter`，`fixed` 子元素就会相对那个祖先定位而不是真正的视口；加在 `html` 上之前凑巧没事是因为 `html` 的盒子本来就约等于视口，但这不是能依赖的保证，拆开更稳。② 想再给 `html`/`body` 写死 `background:#000` 去兜下面说的"状态栏/回弹"背景时，发现这个黑色会被同一个祖先的 `filter:invert` 再翻一次变回白色（截图实测到的），把正文背景也弄白了——`filter` 只扣在 `#app`/`#nowplaying` 上之后，`html`/`body` 自己的 `background` 就不再被这层滤镜影响，可以老老实实写真实的黑/白。
  - **刘海/状态栏和下拉回弹**：这两处都在页面内容的盒子之外，由浏览器直接按 `html`/`body` 的\*真实\*背景色（不是滤镜效果）去填，所以上面"filter 不加在 html 上"这条是前提。`viewport-fit=cover` 让页面延伸到安全区，`body` 的内边距改成 `max(20px, env(safe-area-inset-top))` 这种写法，刘海/齐刘海区域空出来的地方就由 `body` 的真实背景色（深色模式下是真黑）填满；`#nowplaying` 的左右下内边距同样套了 `env(safe-area-inset-*)`，不会被 Home 指示条挡住。另外加了 `<meta name="theme-color">`（切深色变 `#000000`，控制浏览器自己的地址栏/工具栏）和 `apple-mobile-web-app-status-bar-style`（只有"添加到主屏幕"的独立 App 模式才生效，普通 Safari 标签页里是空操作，不影响什么）。
  - **没法自己验证的部分**：这几处（刘海遮挡、下拉回弹的颜色、状态栏样式）都是 iOS Safari 的原生渲染行为，headless Chrome 测不出来，只能靠代码推理加截图验证页面本身没有回归（背景色数值、`#nowplaying` 位置在切换前后完全不变）；真机上到底好没好，需要用户自己看。
  - **全屏模式下退出按钮跑到屏幕外的 bug（2026-10-05 修）**：`body.fs header` 在全屏时把 `header` 变成 `position:fixed`，但 `header` 当时还在有 `filter` 的 `#app` 里面——同一条"filter 的祖先会改变 fixed 元素的定位基准"的规则，这次是从"#nowplaying 定位错位"变成"退出全屏的按钮定位错位"。更隐蔽的是 `body`/`html` 一直没重置默认的 user-agent 外边距（Chrome/Safari 默认给 `body` 8px margin），所以 `#app`（连同不再属于它的 `header`）相对真正视口还多偏了 8px，实测截图里退出按钮直接跑到可视区域右边界之外，摸不到、看不见。改法：把 `header` 从 `#app` 里搬出来，跟 `#nowplaying`一样作为 `body` 的直接子元素（单独套一份 `filter` 保证深色模式下还是反色），`html, body` 补上 `margin:0`，全屏下 `header` 和 `#nowplaying` 的内边距也都换成 `max(原来的像素值, env(safe-area-inset-*))`，不会被刘海/Home 指示条挡住。用无头浏览器量了退出按钮在全屏+深色模式下的实际坐标，确认落在视口内。
  - **全屏模式刘海是白的——五次才找到真正原因（2026-10-05）**：iOS 26 的 Safari **不再读 `theme-color`**，改成取"贴着屏幕顶边/底边的 `position:fixed` 元素"的 CSS `background-color` **属性值**来给状态栏和底部工具栏上色——读的是属性值，不是滤镜处理后的像素。主页顶部没有固定元素，Safari 取 `body` 的真实背景（深色时是真黑），所以没问题；全屏时 `#nowplaying` 铺满整屏、贴着顶边，而它当时靠 `filter:invert` 把字面值 `#fff` 的背景"反"成黑，Safari 读到的是 `#fff`，刘海就是白的。**改法**：`#nowplaying` 自己不再加滤镜，深色模式下背景直接写真黑（`border-top` 改白），滤镜改加在它的内容上（`.progress-row` 和 `.main-row > *`——全屏时 `.main-row` 是 `display:contents`，没有自己的盒子，所以滤镜要加在它的子元素上）；封面以前要再反一次去抵消父元素的滤镜，现在父元素没滤镜了，封面不再加滤镜（`#npCover { filter:none }`）。这样顺带也修好了普通模式下底部工具栏可能被染白的同类问题。
    - **之前走错的几步，记下来免得再犯**：① 播放条 `top` 改成 `env(safe-area-inset-top)` 想让 `body` 背景透出来——没用，Safari 根本不是看哪块像素露出来；② 加了一个只在全屏时出现、盖住刘海的 `#notchBackdrop`——没用，普通 Safari 标签页里 `env(safe-area-inset-top)` 是 0，那一层高度为 0（已删）；③ 以为是 `requestFullscreen()` 让页面进了系统级全屏——错，iPhone 上这个 API 对普通元素本来就不可用，删了也没变化，已恢复（桌面/iPad 上仍然会真全屏）。教训：headless Chrome 测不出 iOS Safari 的状态栏取色规则，这类问题要先查当前 Safari 版本的实际行为，而不是在 CSS 里盲试。
